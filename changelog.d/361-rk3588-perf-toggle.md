### Added

- **RK3588 Performance mode toggle in Settings (#361)** — Settings gains a Performance section, shown only when hardware detection reports an RK3588 deployment, with a toggle over the `taos-rk3588-perf.service` unit (installed and enabled by default on Rockchip boards). `GET`/`PUT /api/settings/rk3588-performance` report board support, unit presence, the toggle's persisted on/off flag and the unit's active state; flipping the switch runs `systemctl start` / `stop`, so the devfreq governors change immediately, and flips the flag file (`/var/lib/taos-rk3588-perf/enabled`) the unit's boot start gates on, so the choice persists across boots. The toggle never enables/disables the unit: systemd's unit-files polkit action carries no unit detail, so no rule could scope enable/disable to this one unit. Because the controller runs as the unprivileged `taos` user, the server installer also installs a polkit rule (`50-taos-rk3588-perf.rules`) granting exactly that user start/stop of exactly that unit, so the toggle is authorised without broader systemd permissions. The rk-llama.cpp unit written by `scripts/install-rk-llama-cpp.sh` now also carries the issue's tuned defaults: `Environment=HYBRID_PATTERN=INT8_STANDARD` and `llama-server` pinned to the big A76 cores via `taskset -c 4-7`. The unit's governor control now lives in a helper (`scripts/taos-rk3588-perf.sh`, installed to `/usr/local/bin/taos-rk3588-perf`): devfreq domains are driven via `governor` and cpufreq policies via `scaling_governor`, and stopping restores the governor recorded when the unit was started (falling back to `simple_ondemand` for devfreq and `schedutil` for cpufreq) instead of writing the devfreq default to the CPUs.
