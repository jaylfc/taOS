# Host-node deletion must cascade to the hosts row (design proposal)

Status: **PROPOSAL** (design task tsk-pitssn). Follows up the taos-website PR #132
review of `GET/DELETE /api/account/devices`. The mapping and the chosen option
are recorded here so the implementation lane can be claimed and built; no code
changes are made in this step.

## The bug

`GET /api/account/devices` (`server/routes/account.py:292`) lists the account's
Headscale nodes, **including the account's paired host node**. `DELETE /api/account/devices/{node_id}`
(`server/routes/account.py:317`) calls `headscale.delete_node(node_id)` -- it
removes the Headscale node but **never touches the `hosts` row**. The only code
that deletes hosts rows is `AccountStore.delete_account`
(`server/accounts.py:1348`, `DELETE FROM hosts WHERE account_id=?`).

Consequence of deleting a host node:

- The Headscale node is gone, so `headscale.node_address_by_name(hs_user, handle)`
  returns `None`, and the relay answers `404 host_unreachable`
  (`server/routes/relay.py:109-122`).
- `GET /api/hosts` (`server/routes/pairing.py:164`) still lists the host, because
  `list_hosts` reads the surviving `hosts` row.
- The `handle` column is `UNIQUE` (`server/accounts.py:94`, backed by
  `idx_hosts_handle` at `server/accounts.py:239`), and there is no single-host
  delete path, so **the handle is claimed forever** -- it can never be reclaimed,
  and `list_hosts` (used by the relay's primary-host resolution at
  `server/routes/relay.py:95-97` and by app-join at `server/routes/pairing.py:432,488`)
  keeps returning a dead handle.

A mobile device (an ephemeral Headscale node with no `hosts` row) deletes cleanly
because it has no handle to orphan. The host is the only device kind that carries
a `hosts` row, so it is the only kind that orphans.

## How the relay maps handle -> Headscale node (the prereq)

The `hosts` table has **no `node_id` / `node_name` column**
(`server/accounts.py:91-95`):

```sql
CREATE TABLE IF NOT EXISTS hosts (
    id TEXT PRIMARY KEY, account_id TEXT NOT NULL,
    headscale_user TEXT NOT NULL, pairing_code TEXT,
    handle TEXT UNIQUE, created_at TEXT NOT NULL)
```

The binding between a `hosts` row and its Headscale node is **by name**: the
host's `handle` (generated by `_gen_host_handle` -> `"h" + secrets.token_hex(5)`,
`server/deps.py:312`) is the Headscale **node name**. The host registers to its
Headscale user namespace (`taos-{account_id}`, `headscale.user_name_for_account`,
`server/headscale.py:75`) with that handle as its `--hostname`, so the node's
`givenName`/`name` equals the handle.

The relay resolves this on every forward-auth request:

1. `hs_user = headscale.user_name_for_account(user["id"])` (`server/routes/relay.py:89`).
2. `handle = x-taos-host-handle` header, or -- for the bare `<username>.taos.my`
   origin -- the account's primary host via `accounts.list_hosts(user["id"])[0]["handle"]`
   (`server/routes/relay.py:90-97`).
3. `addr = headscale.node_address_by_name(hs_user, handle)` (`server/routes/relay.py:111`),
   which matches `(headscale_user, handle)` against Headscale's node list, indexed by
   node `givenName` **and** `name` (`server/headscale.py:207-225`,
   `_rebuild_node_indexes` walks `node.get("givenName")` and `node.get("name")` at
   `server/headscale.py:222`).

The authoritative statement of the mapping is the `node_address_by_name` docstring
(`server/headscale.py:316-319`): *"the host registers with its handle as the
hostname."* For a host, `givenName` == the handle. The same mapping is reused by the
app-join `hosts[]` resolution (`server/routes/pairing.py:439,495`) and by
`resolve_published_site` (joined to `hosts` at `server/accounts.py:1387`, then
`node_address_by_name` at `server/routes/relay.py:167`).

Restated: **handle == Headscale node name; the `hosts` row and the node are joined
only by that string, never by a stored node id.** That is exactly why deleting the
node leaves the row behind: there is no id to join them.

## The two options

### (a) Exclude host nodes from the devices endpoints (conservative)

Stop surfacing the host node in `GET /api/account/devices` and refuse to delete it
from `DELETE`. Rationale: *"your host is not a phone"* -- the devices surface is for
mobile devices (lost-phone revocation), and the always-on host should not be
removable there.

- Pro: the orphan cannot be created through the devices endpoint; no new teardown
  code.
- Con: it only papers over this one deletion vector. A host that leaves the mesh by
  **any other** path -- `tailscale logout`, Headscale admin delete, re-provision,
  still orphans its `hosts` row with **no cleanup path short of account deletion**.
  `GET /api/hosts` keeps listing a dead host, `list_hosts` keeps feeding a dead
  handle to the relay and to app-join, and the UNIQUE handle stays claimed forever.
  It also gives the user no way to remove a stale/decommissioned host binding.
  Excluding the host additionally requires cross-referencing Headscale nodes
  against `hosts.handle` on every list (extra coupling on a read path).

### (b) Cascade cleanup of the hosts row + handle on node delete

When `DELETE /api/account/devices/{node_id}` removes a node whose name matches one
of the account's `hosts.handle` values, also delete that `hosts` row (freeing the
handle) and that host's `published_sites`. Mobile device nodes (no matching handle)
get only the Headscale delete.

- Pro: fixes the bug at its single seam. Deleting a host node now frees its handle
  and drops its row, so `GET /api/hosts` stops listing it, `list_hosts` no longer
  returns a dead handle, and the relay's primary-host resolution skips it. Matches
  the existing teardown philosophy: `delete_account` already cascades hosts +
  `published_sites` + `host_pairings` + join-requests at the app level
  (`server/accounts.py:1336-1355`; `published_sites.host_id` is documented as
  *"teardown is app-level (delete_account)"*, `server/accounts.py:139-141`). The
  `delete_host` primitive this introduces is reusable by future exit paths
  (re-provision, mesh leave).
- Con: needs a `delete_host` method plus the host-vs-device match. The match is
  exactly the relay mapping above: a node is a host node iff its `givenName`/`name`
  is in the account's `hosts.handle` set. A deleted host can no longer serve a
  published site, so the cascade must also clear `published_sites` for that host
  (`resolve_published_site` JOINs `hosts` at `server/accounts.py:1387`, so a missing
  row 404s cleanly without it -- but stale `published_sites` rows are data rot to
  remove, same app-level teardown as `delete_account`).

## Decision: (b) cascade cleanup

(b) fixes the orphan at the one seam that causes it, and provides the reusable
`delete_host` primitive; (a) is a read-path band-aid that leaves handle-claimed-
forever and dead-host-listed alive under re-provision and every other exit. Because
the handle<->node binding is by-name (documented in the section above), matching a
node to its `hosts` row is unambiguous: a node is the account's host node iff its
`givenName` or `name` equals an `accounts.list_hosts(account_id).handle`.

## Implementation sketch (future lane, taos-website)

1. `AccountStore.delete_host(account_id, handle)` (`server/accounts.py`) -- a single
   transaction: look up the `hosts` row by `(handle, account_id)`; delete its
   `published_sites` (`DELETE FROM published_sites WHERE host_id = ?`, keyed on the
   host's `id`); then delete the `hosts` row. App-level cascade, mirroring
   `delete_account`. Returns whether a row was removed.
2. `DELETE /api/account/devices/{node_id}` (`server/routes/account.py`) -- after the
   existing ownership check, read the matched node's `givenName`/`name`; if it
   equals an account `hosts.handle`, call `delete_host` (best-effort, logged) in
   addition to `headscale.delete_node`. Order: delete the Headscale node first (the
   user asked to remove the device), then cascade the `hosts` row +
   `published_sites`; a failed DB write leaves the row behind, which is today's
   behaviour -- never worse.
3. Tests (`tests/test_device_removal.py`): add a host node (`givenName`/`name` == a
   handle written to `hosts`, plus a `published_sites` row on that host) and assert
   deleting it removes the `hosts` row + `published_sites` while still calling
   `headscale.delete_node`; assert a mobile device node (no handle) deletes the node
   only and leaves `hosts` untouched; assert cross-account isolation and the 503
   outage path are unchanged.

No controller (tinyagentos) change is required to establish or fix the mapping: the
relay, mesh join, and `--hostname` registration already key off the handle on the
taos-my side, so this is a taos-website-only decision and fix.
